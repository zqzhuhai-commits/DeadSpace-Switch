# 0.3.2 后续：映像、嵌套调用和堆管理

基线：`da796f5040162d6a7760122096414a0c90354b41`。本轮继续修复实际生命周期执行器，不生成 NSP，不代表游戏画面已出现。

## 映像地址修复

`GuestImage::base` 已为 `0x10000000`，ELF 的 LOAD 地址在存储中应保留为相对偏移。旧镜像实现又给偏移加 `0x10000000`，经 read/write 再加基址后，第二份映像实际落在 guest `0x20000000 + va`；该区域正是执行器的栈地址，普通写入还会让两份数据分离。

本轮删除第二次偏移、映像复制及重复重定位写入。原 `0x10000000 + va` 地址和导出符号保持，存储按原始 LOAD 末尾大小分配，相比旧 vector 长度减少 **268,435,456 字节（256 MiB）**。这是存储布局差值，尚不是实机进程内存测量。

新增共享 `GuestLayout` 和 `image_range`：限制映像最多 64 MiB、检查存储边界/段权限，并静态检查映像、栈、堆互不重叠。GuestImage 的读、写、执行检查均使用该函数；原版库 SHA1 白名单仍保持不变。

## 嵌套调用修复

旧 `guest_call` 在 EAIO Startup 等 JNI 回调进入 guest 时，重新把 SP 放到全局栈顶，可能覆盖暂停的外层函数。现在根据外层当前 SP 向下安排参数区并保持 8 字节对齐，预留间隔和最小可用栈空间；越界或异常 SP 会明确拒绝。

`GuestCallScope` 对整数寄存器、扩展寄存器、CPSR、FPSCR，以及 returned/pending/budget/fault 状态做成对保存和恢复。嵌套调用正常或抛异常都会恢复外层现场，服务返回值由调用方单独写回，不再把子调用 r1-r3/r12 的残留带回外层。顶层成功调用继续保留 0.3.2 的调用间寄存器行为；该兼容行为仍需真实库回归。

## 堆管理修复

旧 free 只检查地址，未释放；realloc 无论旧块大小都读取新长度，扩容会越界读取。

现在使用 `GuestHeap`：16 字节对齐、空闲块复用、切分及相邻块合并；非法地址和重复释放会被拒绝。realloc 仅复制 `min(旧请求大小, 新大小)`，失败保留原块；非空指针 realloc 到零会释放并返回 0。calloc 检查乘法溢出及大小上限，对复用块实际清零。分配后清零/复制若抛出异常，撤销新块。

原有单次 32 MiB、堆区域 64 MiB 的诊断限制保留；这不是完整 bionic 分配器，分配失败仍会阻塞诊断而非模拟完整 errno/内存回收行为。JNI 局部引用和字符串副本仍未回收，不能因此认定已经适合长期运行。

## 剩余工作

- `pthread_create` 和真实 guest 线程调度仍未实现。现有 pthread_self、锁、信号量/TLS 仍是单线程诊断模型；本轮上下文作用域只解决嵌套调用，不能替代线程调度器。
- 需用支持的 PSV 原始库重跑启动，确认正确 JNI 参数及映像/栈修复后的实际停止点，再接通真实 GL、音频、输入和存档。
- 高清包准备流程保持；尚无高清纹理上传或真机画面证据。4096×4096 RGBA8 基础层需 64 MiB，后续应在主机渲染侧按需处理，不能直接塞进当前单次 32 MiB 的 guest 分配接口。
- 最终仍交付程序和资源全部内置的独立 NSP；目前没有可玩 NSP 产物。
