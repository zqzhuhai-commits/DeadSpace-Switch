# 0.4.4-jitrange

实机 0.4.3 日志确认设置复制错误已经越过，游戏构造函数、JNI、活动、Surface 和第 1 帧均返回。用户随后只见菜单十字。最新启动日志没有第 2 帧返回记录；diagnostics.log 前段包含旧版追加内容，不能把旧错误当作本次失败。

检查发现 ARM64 CodeMemory 路径每次 protect 都调用 libnx 通用 executable transition。该调用会同步整个 32 MB 代码缓存，导致每个新基本块和重链接产生大量全缓存操作。单独的 invalidate 原本没有执行范围同步。本轮改为：对实际修改范围先清理 RW 别名的数据缓存，再失效 RX 别名的指令缓存；CodeMemory protect 不再重复全缓存同步。保留旧式映射路径所需的权限转换，保留启动/清空缓存时上游显式要求的 invalidate_all。

该范围同步方案与旧版可运行分支使用的方式一致。它是明确的性能问题修正，但目前尚未实机证明它完全解释这次黑屏。

## 检查

- 针对性回归通过：新代码 16 字节、已有块重链接 4 字节的 RW/RX 地址和清理顺序正确；每块 protect 不进行全量转换；非法/零长度范围及旧映射路径处理正确。测试使用模拟 libnx API，不是实际 Switch CPU 缓存验证。
- 相同回归在旧实现上按预期失败：`CodeMemory protect performed full-buffer transition`。
- 发布的依赖补丁对固定原始源码 apply --check 通过，构建实际使用的依赖已同步修改。
- Windows 原游戏库参考运行 600 帧，新增日志显示第 1 帧没有 GL 提交，第 2 帧执行真实资源挂载后开始纹理上传/绘制；这只是主机证据，不代表实机帧率。
- Switch 核心和程序编译/链接通过；NSP 已独立解密，检查哈希链、CNMT、程序及全部 1,748 个资源文件。

## 测试

安装 `DeadSpace-Mobile-ZH-0.4.4-JitRange.nsp`，保留已有 SD 存档。无需再运行启动检查小包。

新日志保留 `/switch/deadspacemobile/startup-latest.log`，版本应为 `0.4.4-jitrange`。增加了帧开始、加载阶段心跳、GL/资源计数和阶段性绘图统计，便于区分耗时加载、线程等待和绘图错误。

若仍只有十字，运行约一分钟后提供新日志，重点比较是否已越过第 2 帧和资源挂载阶段。未在目标机运行此新包，不承诺 FPS、声音或全流程完成。完整游戏安装包及密钥不上传公共仓库。
